## 3. Findings 1 to 4 of the earlier review

### Finding 1 (P1): PARTIALLY FIXED

Fix: `tools/release/deploy.py:619` (`RunState.state_before_rollback`), `:665` (written with
every record), `:1180-1182` (automatic path sets `DEPLOYMENT_STOPPED` once), `:1508` (owner
path: `previous.get("state_before_rollback") or previous["state"]`), `:1662-1687` (`recover`
returns to `DEPLOYED_AWAITING_ACCEPTANCE` only when the stored origin is that state, otherwise
`FAILED_HELD` / `RECOVERED_ON_RELEASE_NOT_ACCEPTABLE`).

The original scenarios, reproduced with my own probe (ingress started by hand between steps):

```
extra_backend           deploy -> FAILED_HELD SECOND_BACKEND          rb FAILED
   recover: FAILED_HELD / RECOVERED_ON_RELEASE_NOT_ACCEPTABLE   accept: REFUSED ACCEPTANCE_NOT_PENDING   known-good: None
   recover again: RECOVERY_NOT_APPLICABLE                        accept: REFUSED ACCEPTANCE_NOT_PENDING
restarts_after_up       deploy -> FAILED_HELD HEALTH_CHECK_FAILED     (same four results)
volume_changes_after_up deploy -> FAILED_HELD VOLUME_IDENTITY_CHANGED (same four results)
ACCEPTANCE_FAILED -> rollback interrupted at first sed: ROLLBACK_INTERRUPTED sbr=ACCEPTANCE_FAILED
   recover: FAILED_HELD / RECOVERED_ON_RELEASE_NOT_ACCEPTABLE   accept: REFUSED ACCEPTANCE_NOT_PENDING   known-good: None
```

All four are now held. Further sequences tried, all held and `accept` refused:

- deployment stopped with no automatic rollback approved (record has `state_before_rollback:
  null`), then an interrupted owner rollback: origin becomes `FAILED_HELD`; `recover` holds;
- failed deployment, automatic rollback interrupted, then two interrupted owner retries: origin
  stays `DEPLOYMENT_STOPPED` through attempts 1 to 3; `rollback_history` has 2 entries;
- stale `ROLLBACK_IN_PROGRESS` (process killed with no handler): the origin is already in the
  record on disk; `accept` `ROLLBACK_INCOMPLETE`, `recover` holds;
- a record with no `state_before_rollback` key (as `37f3aa6` wrote): `recover` gives
  `FAILED_HELD` / `RECOVERED_ON_RELEASE_NOT_ACCEPTABLE`; an owner retry on it takes the origin
  from the current state (`FAILED_HELD` or `ROLLBACK_INTERRUPTED`), never the acceptable one.
  This is conservative: an older record of a good release whose owner rollback was interrupted
  is also held (see N-5);
- interruption matrix (section 5) and 2500 random call sequences mixing `run`, `accept`,
  dry-run, `manual_rollback`, `recover`, injected faults and hand-changes to the mock host: no
  failed deployment was accepted and no accept passed with a rollback unfinished.

**What is not fixed** (found by reading `:1508`, then confirmed): the origin is recorded once
and kept for the life of the release record, across rollback *episodes*, not only across
attempts of one rollback. If the first rollback of a good release began while it was awaiting
acceptance and `recover` put it back, a LATER failed acceptance does not change the stored
origin, so `recover` after a second unfinished rollback makes it acceptable again. See N-1.

## 4. New findings

### N-1. P1: a release whose acceptance failed can still be accepted through `recover`

`tools/release/deploy.py:1508` (origin kept from any earlier rollback), `:1662` (`recover`
trusts it), `:1769-1776` (`accept(passed=False)` leaves it unchanged).
`docs/release/PIPELINE_ARCHITECTURE.md` 3.7: "A deployment that stopped on a stop condition,
or whose acceptance failed, can never become acceptable through `recover`". Code comment at
`deploy.py:1670-1671` says the same.

Observed (frontend-only release; both rollbacks interrupted at their first `sed`, so the host
never left the release image):

```
deploy                      -> DEPLOYED_AWAITING_ACCEPTANCE
owner rollback #1 (Ctrl-C)  -> ROLLBACK_INTERRUPTED   sbr=DEPLOYED_AWAITING_ACCEPTANCE
recover                     -> DEPLOYED_AWAITING_ACCEPTANCE / RECOVERED_VERIFIED_ON_RELEASE   (as designed)
accept --result fail        -> ACCEPTANCE_FAILED      sbr=DEPLOYED_AWAITING_ACCEPTANCE (unchanged)
owner rollback #2 (Ctrl-C)  -> ROLLBACK_INTERRUPTED   sbr=DEPLOYED_AWAITING_ACCEPTANCE
recover                     -> DEPLOYED_AWAITING_ACCEPTANCE / RECOVERED_VERIFIED_ON_RELEASE
accept --result pass        -> ACCEPTED, known-good pointer moved to this release
result files: DEPLOYED_AWAITING_ACCEPTANCE, ROLLBACK_IN_PROGRESS, ROLLBACK_INTERRUPTED, DEPLOYED_AWAITING_ACCEPTANCE,
              ACCEPTANCE_FAILED, ROLLBACK_IN_PROGRESS, ROLLBACK_INTERRUPTED, DEPLOYED_AWAITING_ACCEPTANCE, ACCEPTED
```

The same end state when rollback #1 FAILED (ingress stop refused) and the operator re-pinned by
hand before the first `recover`, and when rollback #2 failed at the `up` and the operator
re-pinned by hand. Straight after the failed acceptance, without the second rollback, `accept
--result pass` is refused (`ACCEPTANCE_NOT_PENDING`), so `recover` is what reopens it.

Why it matters: this is the fourth case of the earlier finding 1 (failed acceptance made
acceptable), reached by a longer route, and it contradicts the sentence the fix added to the
architecture document. It needs a person to run `recover` and then `accept --result pass`, the
release had passed its deployment verification, and every step stays in the numbered result
files. It is narrower than the original, but the stated rule does not hold. The committed test
`test_recover_never_turns_a_failed_acceptance_into_an_acceptable_release` covers only a
release with no earlier rollback. A possible narrow repair (not applied): take the stored
origin only while the record is in an unfinished or failed-rollback state, and otherwise take
the current state, so a later `ACCEPTANCE_FAILED` replaces it.

### N-2. P2: `ROLLED_BACK` / "verified-on-previous-images" while a never-applied service runs the release image

`deploy.py:1361-1370` (`_pins_restored` checks the pin only), `:1412-1428` (image checked for
touched services only), `:1245`. `PIPELINE_ARCHITECTURE.md` 3.7: "`ROLLED_BACK` only after
every service is confirmed healthy on its previous image".

Probe: backend+frontend release, backend unhealthy so only it was applied; `compose.env` pins
both to the release. Someone then runs `docker compose up` for the frontend by hand (the exact
hazard the earlier finding 3 named). The owner rollback follows:

```
after hand `up frontend`: images {backend: NEW, frontend: NEW}
owner rollback -> ROLLED_BACK  pins {backend: OLD, frontend: OLD}  images {backend: OLD, frontend: NEW}
   rollback.status COMPLETED_VERIFIED  host_state verified-on-previous-images  rollback.services ['backend']
recover: RECOVERY_NOT_APPLICABLE
```

The frontend line is pinned back but the frontend is not recreated or checked, so the record
says verified while one service of the release still runs the release image and now disagrees
with `compose.env`. `recover` would call the same host "unknown". It needs an out-of-band
action on the host; without one the rollback is correct. The image check on touched services
only predates this delta; the delta added the claim and the pin-only check for the others.

### N-3. P2 (predates this delta; reported because it loses `state_before_rollback`): a second `run`, including a dry-run, replaces an unfinished-rollback record

`deploy.py:622-645` (`run` starts a fresh `RunState` and writes a result without looking at the

```
before: FAILED_HELD  sbr=DEPLOYMENT_STOPPED  stop=SMOKE_FAILED  rollback.status FAILED
dry-run of the same release -> FAILED_NO_CHANGE PREFLIGHT_FAILED (host is not at the rollback target)
```

Same with `--execute`. The release does not become acceptable (a later `run` can only reach

the release image with a failed rollback, the origin and rollback block are gone from the
latest record (the numbered files keep them), and both `recover` and `rollback` refuse, leaving
only recovery by hand. Not introduced by `84706a9`.

### N-4. P3: document says a persistent write failure "ends `FAILED_HELD`"

`PIPELINE_ARCHITECTURE.md` 3.7 ("If it still fails, the step is not taken and the rollback ends
`FAILED_HELD`"). True when only the journal append fails. When the rename keeps failing, the
final record cannot be written either: the command raises `PermissionError` and the record on
disk stays `ROLLBACK_IN_PROGRESS` (probe in section 3, finding 2). When the failure is on the
approval file, the result is `ROLLBACK_INTERRUPTED`. All are held and unacceptable.

## 5. What I checked and found sound

- **Retry loop (C i).** Bounded at 40 attempts per write; re-raises on the last; a write that
  finally fails stops the step (`ROLLBACK_NOT_RECORDED`) and no further rollback command is
  issued; the host lock is released.
- **`_unpin` and the pre-check (C ii).** The `sed` is anchored on the exact release line, so
  no other line can change. All lines are examined before the first edit. Observed:

  ```
  never-applied line shows a third value (first attempt)  -> HOST_STATE_UNEXPECTED, 0 host writes, env unchanged, approval not consumed
  applied line shows a third value (first attempt)        -> HOST_STATE_UNEXPECTED, same
  applied line already on the previous pin (first attempt)-> HOST_STATE_UNEXPECTED, same
  never-applied line already on the previous pin (first)  -> accepted, ROLLED_BACK
  never-applied line third value (retry)                  -> HOST_STATE_UNEXPECTED, 0 host writes
  applied line already on the previous pin (retry)        -> accepted, ROLLED_BACK
  line changed between the pre-check and the sed           -> FAILED_HELD "frontend: the previous pin was not written"; the foreign value left alone
  ```
- **`_pins_restored` (C iii).** Every automatic-rollback test still passes; in the matrix below
  all 18 retries after an interrupted automatic rollback and 28 after an owner-requested one
  ended `ROLLED_BACK` with pins and images on the previous values.
- **Approval consumption (C iv).** Order on a normal run: in-progress record, then consume,
  then first host write (`[('consume','ROLLBACK_IN_PROGRESS'), ('first-step','ROLLBACK_IN_PROGRESS', consumed=True)]`).
  If the in-progress record cannot be written: `ROLLBACK_NOT_RECORDED`, record unchanged,
  approval not consumed, only the lock taken and released. If consuming raises: no rollback
  step is issued, record `ROLLBACK_INTERRUPTED`, `accept` refused. I found no path where a
  rollback step runs with the approval unconsumed, or the approval is consumed with no
  in-progress record.
- **Earlier N1/N2 behaviour (C v).** Backend+frontend rollback interrupted at every command
  after the in-progress record, Ctrl-C and killed-with-no-handler, both paths (86 cases):
  18 + 23 `ROLLBACK_INTERRUPTED`, 19 + 24 + 1 `ROLLBACK_IN_PROGRESS`, 1 `FAILED_HELD` with
  `COMPLETED_VERIFIED`. The last two single cases are the lock-release window already recorded
  as finding 6 of the earlier review and now stated in architecture 3.6 (the automatic one
  also leaves the host lock, so the retry is refused until it is removed). None was
  `ROLLED_BACK`; `accept` was refused in all 86; `recover` said `ROLLED_BACK` only with pins,
  images and health all on the previous values (39 cases), never made the failed deployment
  acceptable, and issued no host write in any probe (asserted on every call).
- **Expiry.** Window ending during an owner rollback: `FAILED_HELD` / `APPROVAL_EXPIRED`, the
  refused step left `STARTED`; not extended.
- **Nothing removed.** The delta deletes no command, schema field or test; `mypy --strict`
  and `ruff` clean.
- **Mutation check (D).** 20 mutants on lines this delta changed, scratch copy from
  `git archive 84706a9`, `tests/release` with the one git-dependent test deselected (baseline
  301 passed), each kill confirmed by a second run: **15 killed, 5 survived.** Killed: origin
  test removed in `recover`; origin reset on each attempt; origin not derived on a first
  attempt; origin always overwritten; origin not recorded; `_unpin` on touched services only;
  `_pins_restored` removed; `_pins_restored` on touched only; frontend recreate not flagged;
  approval consumed outside the recorded section; rename without retry; rename failure
  swallowed; stale `held_reason` kept; held outcome recorded as another state; failed owner
  rollback reporting ingress not stopped. Survived: M07 (`_unpin`'s first-attempt guard;
  equivalent, the pre-check enforces the same), M08, M09, M14, M19 (N-7). Each new test
  therefore fails when its own safeguard is removed, except that the journal-append retry has

- **Documents (E).** `N1_N2_INDEPENDENT_REVIEW_20261114.md` is byte-identical to
  `outputs/release-pipeline-20261114/N1_N2_INDEPENDENT_REVIEW.md` (sha256

## 6. What rests only on the mock

- Every result here. The mock's `up`, `stop`, `sed` and `cp` are atomic and instant; a real
  `docker compose up --wait` that is killed or times out can leave states the mock never shows.
- The transient "Access is denied" was injected, not observed (0 of 4000 natural failures in
  this session). That 40 attempts over about two seconds is long enough on the real controller
  is unverified.
- `recover`'s judgement of "on the release" or "on the previous images" depends on image-id,
  health and pin reads whose real output formats are only simulated.
- The hand-changes in N-1, N-2 and the random search are edits to the mock's state standing in
  for what an operator might do on the host.
- No CLI-level run (`release.ps1`) was made; `deploy.*` functions were called as the tests call
  them, with `render.validate_release_config` stubbed.
